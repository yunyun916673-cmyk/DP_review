# 魔法封印
## 題目意思
你有許多個魔法封印陣，每個封印陣都有對應的「寬度」與「能量高度」。
如果要把一個封印陣嵌套放入另一個封印陣中，外層封印陣必須在「寬度」與「能量高度」上都 嚴格大於 內層的封印陣（也就是說 w1 < w2 且 h1 < h2）。
請計算在給定的一組封印陣中，最多可以將多少個封印陣層層嵌套在一起，發揮最大的魔法共鳴。
## 輸入格式
第一行包含一個正整數 t (1 <= t <= 20)，代表測試資料的數量。
每筆測試資料包含一個正整數 m (1 <= m <= 20000)，表示封印陣的數量。
接著會有 2m 個正整數 w1, h1, w2, h2, ..., wm, hm，其中 wi 和 hi 分別表示第 i 個封印陣的寬度與能量高度。
## 輸出格式
針對每一筆測資，輸出一個整數，代表最多可以嵌套的封印陣總層數。
## 範圍限制
1 <= t <= 20

1 <= m <= 20000

1 <= wi, hi <= 1000

# 魔法封印
## 題目想法
一開始看到這道題目時，直覺想到這不就是 ZeroJudge 裡面很有名的「飛黃騰達」嗎？原本以為是完全一樣的概念，但仔細一看才發現陷阱：這題要求寬度與高度都必須「嚴格大於」（不能等於），這對原本直觀的排序與轉移邏輯產生了極大的影響。

## 解題過程
運用物件導向的思維寫了 struct DP 來封裝單筆測資的運算。實作上先對輸入的兩個維度進行排序，接著把問題降維，針對第二個維度（高度）跑 1D LIS（最長遞增子序列）。而在實作 1D LIS 時，使用了 lower_bound 搭配陣列的二分搜尋法（耐心排序法）來達到最佳效能。

## 解題方法思考
這題最核心的關鍵在於排序機制的設計。如果是正常排序（寬度由小排到大，寬度相同時高度由小排到大），在跑 LIS 時，相同寬度的娃娃可能會因為高度遞增而被誤判為可以互相嵌套，但實際上寬度相同是無法嵌套的。

為了避開這個問題，我自定義了排序函式：當寬度相同時，讓高度「由大排到小」。
這樣做非常巧妙：對於相同寬度的元素，因為高度是遞減處理的（從最不可能排到最有可能），在 LIS 的 tails 陣列中，它們頂多只會更新同一個位置，絕對不可能接在彼此後面形成遞增長度，完美且優雅地解決了「嚴格大於」的限制條件！

## 複雜度分析
### 時間複雜度：
排序部分耗費 O(M log M)，計算 LIS 過程中使用迴圈搭配二分搜尋法同樣耗費 O(M log M)，因此總時間複雜度為 O(M log M)，在 M <= 20000 且 T <= 20 的限制下能輕鬆通過。

### 空間複雜度：
使用 vector 儲存 M 個資料配對，以及一個長度最大為 M 的 tails 陣列，空間複雜度為 O(M)。

## 學習心得
這次解題最大的收穫，是體會到「改變排序策略就能省去大量複雜判斷」的美妙之處。原本可能要在 LIS 裡面加一堆 if-else 去紀錄和阻擋相同寬度的更新，但只要轉個彎，利用次要排序的「反向」，就能讓原有的 O(N log N) LIS 演算法不改一兵一卒地適應嚴格遞增的條件，這是一個非常實用且精美的技巧！
